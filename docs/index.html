Two processes look at one screen. Only one of them can lie.

  1. vehfeed → vehicled /dev/vehicle: devctl SET
  2. vehicled → cluster: ionotify pulse + devctl GET
  3. cluster → QNX Screen: screen_post_window (the path that can lie)
  4. QNX Screen → telltale: screen_read_display
  5. vehicled → telltale: devctl GET_SINCE, every check
  6. telltale → QNX Screen: safe layer, z-top
  7. telltale → cluster: SIGKILL if hung, wrong or blank; slm or a shell loop respawns it

It reads the glass, not the renderer's word

Every 20 ms the monitor reads back the digit, lamp and tick regions and decodes them with the glyph atlas the cluster draws with. In the BLANK and MISDRAW runs a renderer self-report would have passed 60 of 60; the read-back caught all 60.

screen_read_display

The truth is a pathname

vehicled serves the vehicle state at /dev/vehicle. The cluster is woken by an ionotify pulse; the monitor asks for everything since its last check.

resource manager · devctl

Its own type

Feeder, vehicled, renderer and monitor each run in their own secpol type; 22 of 22 policy checks pass on the target, 13 of them denials. The bench ran without the policy loaded.

secpol

Hung or starved?

The monitor runs at FIFO 60, the renderer's draw thread at 20. On a stall it reads /proc to tell a hung renderer from a starved one, and leaves a starved one running while its window is readable: 0 of 50 STARVE runs were restarted.

SCHED_FIFO · /proc

Cover first, then repair

A safe layer with the true values goes on top, then SIGKILL, respawn, and a verified frame before the glass is handed back.

screen_post_window · slm

No machine learning, on purpose: the check is a deterministic glyph decode, so the same frame always gets the same verdict.

Questions a QNX engineer would ask.

Does this really run on QNX?

Yes. C built with qcc from QNX SDP 8.0, running on the QNX Everywhere Quick Start image: an x86_64 guest under QEMU (TCG) on an Apple-Silicon Mac. No hardware was used, so every timing here is QEMU timing.

Why read pixels instead of trusting the renderer?

Because the renderer is the part that fails. In the BLANK and MISDRAW runs, a self-report of "intended vs truth" would have passed 50 of 50 and 10 of 10; reading back the composed display caught all 60.

What does QNX give it that a plain process would not?

A monitor is only worth something if a broken renderer cannot take it down. Telltale is its own process in its own secpol type at FIFO 60; it reads the truth from a resource manager and the glass from Screen, and restarts the renderer while everything else keeps running. The policy is exercised by the on-target suite; the bench and the incident above ran without it.

What is real, and what is replayed or injected?

Real: the QNX target, Screen composition, read-back, decode and recovery. Replayed: real CAN speed from comma2k19, fed into /dev/vehicle. Injected: the faults, by the project's own injector. Not verified yet: the gear indicator.

Is there AI in it?

No, on purpose. The check is a deterministic glyph decode: the same frame always gets the same verdict.

How do I reproduce the numbers?

With the SDP installed: make target, boot the guest with scripts/run_qemu.sh, then make test-target and scripts/bench_all.sh run. scripts/bench_all.sh report regenerates every table from the committed CSVs; see DEMO.md.
